# 12-v38 桌面黑屏与入口丢失（现象→真因→解法）

> v38 集中修复了三处「看起来像软件没了」的问题，根因分别落在 APK 路径、SELinux 标签、日志属主。
> 三处都已在真机（小米 Pad 6 Pro / LineageOS / KernelSU）双模式回归通过。

---

## 1. 非 root（proot）桌面黑屏：X server 静默死亡

**现象**：非 root 模式点「进入桌面」，屏幕全黑，`termux-x11` 起来了但 `x11.log` 是 0 字节，proot 里没有 `/tmp/.X11-unix/X0`，后面 XFCE 一整套组件全都不启动。

**真因**：启动脚本用 `pm path com.termux` 拿 APK 路径当 `app_process` 的 CLASSPATH 去起 Lorie（X server）。但脚本是 App 自己用 `am`/脚本拉起的，运行在 `untrusted_app` 域，此时 `pm path com.termux` 返回：

```
cmd: Failure calling service package: Failed transaction (2147483646)
```

于是 `APK` 变量成了这串错误文本，`app_process` 拿着一个不存在的 jar 直接失败，X server 连一行日志都没写就死了。X socket 不存在 → proot 里没有显示 → 黑屏。

**解法**：不依赖 `pm`。App 在 `prepare()` 时用 `ctx.getApplicationInfo().sourceDir` 把自身 APK 绝对路径写进 `$FILES_DIR/.apk-path`（App 自己写的文件天然 App 属主、可读）；启动脚本按可靠性排序取：

```sh
APK=$(cat "$FD/.apk-path" 2>/dev/null)
[ -f "$APK" ] || APK="$TERMUX_APP__APK_PATH"
[ -f "$APK" ] || APK=$(pm path com.termux 2>/dev/null | grep -v split | head -1 | sed 's/package://')
```

并在拉 proot 前显式检查 X socket 是否存在，不存在就把 `x11.log` 尾巴打出来并 `exit 1`，不再让错误被埋在黑屏后面。

## 2. proot 报 `/bin/bash` not found（文件明明在）

**现象**：APK 路径修好后，proot 仍直接报：

```
proot error: '/bin/bash' not found (root = .../ubuntu, cwd = /root, $PATH=(null))
```

但 `ls /data/data/com.termux/files/ubuntu/bin/bash` 确实存在。

**真因**：系统包是 root（ksu 域，无 MLS 类别）解压/恢复出来的，整盘标签是 `u:object_r:app_data_file:s0`；而 App 进程在 `untrusted_app:s0:c167,c256,c512,c768`。MLS 类别约束下：App 能 `stat`（看不到 denied），但 `readlink`（解析 `/bin` 符号链接）和 ELF `exec` 全部 EACCES。proot 第一步就要解析 guest 的 `/bin`，读不了 → 报"文件不存在"。

**解法**：新增 `fix_selinux.sh`，以 root 把 rootfs 标签对齐到 `$FILES_DIR` 的标签：

```sh
CTX=$(stat -c %C "$FD")        # 带类别的 App 目录标签
chcon -R -h "$CTX" "$R"        # 对齐 rootfs
```

- **幂等**：标签一致直接退出，开销一次 stat；
- **护栏**：`grep -qs " $R/" /proc/mounts` 有挂载就中止（见铁律 1，`chcon -R` 穿透会改坏真实 `/dev`）；
- **探测不能用 `exists()`**：`File.exists()` 走 `access(F_OK)`，同样要解析符号链接，标签不匹配时也返回 false，会被误判成"rootfs 还没导入"而放过检测。正确做法是直接 `readlink(rootfs/bin)`，EACCES 即判定标签不匹配。

触发时机：root 模式每次启动 `fix_perms.sh` 里调一次；非 root 模式由 Java 的 `ensureSelinuxLabels()` 探测，读不到 rootfs 且确实拿得到 su 时才修，读得到就不打扰用户。

## 3. root 模式「没有浏览器和输入法」

**现象**：用户报告 root 模式下 XFCE 桌面里找不到浏览器图标、输入法也没了；rootfs 重新「导入系统包」或从备份恢复后，`~/Desktop` 变空。

**真因**：这些桌面入口（浏览器 / 中英切换 .desktop、默认浏览器 helper、fcitx5 自启）是早前会话手工放进去的，不在系统包里。一旦 rootfs 被覆盖/恢复就丢了——不是"软件被删了"，是入口文件没了。

**解法**：新增 `install-desktop-icons.sh`，每次启动桌面都幂等补齐：

- `~/Desktop/` 下 4 个 .desktop（浏览器 / 中英切换 / 终端 / 文件管理）；
- `~/.local/share/xfce4/helpers/chrome-browser.desktop` + `~/.config/xfce4/helpers.rc` 设默认浏览器（放用户目录而非 `/usr/share`，proot 下 root:root 不可写）；
- `~/.config/autostart/fcitx5.desktop` 输入法自启。

内容相同则跳过（用 `cmp -s` 比较，尊重用户手改）。root 侧由 `start-desktop.sh` 拷进 chroot 调用；非 root 侧由 `start-xfce-noroot.sh` bind 进 proot 的 `/root` 调用。从此 rootfs 再怎么覆盖都不会丢入口。

## 附带修复：日志属主挡住 proot 重定向（铁律 5 的具体发作）

**现象**：以上都修完后，仍偶发桌面组件一个都不起。

**真因**：root 会话先把 `/tmp/xfce.log` 写成 root:root 644，`/tmp` 是 1777 带 sticky，App uid 既不能覆盖也不能删。而非 root 启动脚本里 `nohup xfwm4 >/tmp/xfce.log 2>&1 &` 的重定向一失败，**shell 直接跳过整条命令**（铁律 5）——xfsettingsd/xfwm4/panel/xfdesktop 一个都起不来，黑屏还查不到原因。

**解法**：所有日志改写到 `$HOME/.runtime`（App 属主、700）；root 侧 `start-desktop.sh` 启动前先把 `xfce.log/dbus.log/icons.log` 建成 alan 属主 644；非 root 侧 `start-desktop-noroot.sh` 把日志 `$LOG` 指向 `/root/.runtime` 并清掉历史 root 属主残留。

| root（chroot） | XFCE 完整跑起来，Chrome 干净打开无错误弹窗，fcitx5 运行中 ✅ |

**已知无害告警**：首次启动 `icons.log` 出现 `mktemp: ... No such file or directory`（当时 TMPDIR 目录不存在），因 `_put()` 有 `|| return 0` 兜底、最终靠 fallback 写完，图标全部生成正确；仅幂等比较失效（每次重写内容相同的图标），不影响功能。可后续把 `mktemp` 的临时目录固定到 `$H/.runtime`。
