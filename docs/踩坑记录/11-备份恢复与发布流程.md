# 11 - 备份恢复与发布流程踩坑

> 本文件记录 v36→v37 自测中真实复现、已修复的问题。每一条都能让「看起来写对了」的功能实际不可用，排查成本很高。

## 1. `su -c '... "$1"' sh <参数>` 在 Android su 上拿不到参数

**现象**：从菜单点「恢复备份」，日志是 `ERR 备份包不存在：`（路径为空）；同一脚本用 `sh restore-rootfs.sh /sdcard/xxx.tar.gz` 命令行直跑完全正常。

**原因**：Android 的 su（KernelSU / Magisk）执行 `-c` 时只把紧跟的命令字符串交给 shell，**不会把后续位置参数透传成 `$0/$1`**。脚本里的 `SRC="$1"` 因此是空串，在第一步参数校验就退出。

**修法**：把路径做 POSIX 单引号转义后直接拼进命令字符串：

```java
private static String shellQuote(String s) {
    return "'" + s.replace("'", "'\\''") + "'";
}
new ProcessBuilder(suBin, "-c", "sh " + SCRIPT + " " + shellQuote(path));
```

转义同时防住了文件名含空格/单引号时的拆分与注入。

## 2. `/dev/null` 不存在时，`2>/dev/null` 会让整条命令被跳过

**现象**：恢复脚本的护栏始终报「仍有挂载未卸载」，但 `umount` 看起来一条都没执行。

**根因链**：
- 这台设备 `/dev` 的 tmpfs 挂载丢了，`/dev` 退化成 erofs 根上的只读空目录，`/dev/null` 不存在；
- shell 遇到 `cmd 2>/dev/null` 时**先做重定向**，创建失败就报 `can't create /dev/null: Read-only file system` 并**不执行 cmd**；
- 脚本里 19 处 `2>/dev/null`，于是 pkill、umount、mkdir 全部静默跳过，护栏自然永远拦截。

**修法**：备份/恢复/权限/打包脚本一律改成把 stderr 追加到自己的日志文件（`2>>"$LOG"`，日志在 `/data/data/com.termux/files/log/` 可写），不依赖 `/dev/null`。`$( ... 2>>"$LOG" )` 也不会污染 stdout 取值。

**设备侧恢复**：`setprop sys.powerctl reboot` 和 `reboot` 命令在 `/dev` 异常时都会失败（属性服务/p ty 都依赖 /dev），最后用内核 sysrq 才重启成功：

```sh
echo 1 > /proc/sys/kernel/sysrq
echo b > /proc/sysrq-trigger
```

重启后 init 会重新挂 `tmpfs /dev`，`/dev/null` 恢复。

## 3. AlertDialog 的 `setItems` 在深色主题下渲染成空白

**现象**：「选择要恢复的备份」对话框只剩标题、说明、「取消」，中间一大片空白，用户根本选不了包；`uiautomator dump` 里连 ListView 节点都没有。

**修法**：不再用系统列表，改成 `setView()` 自建 `ScrollView + LinearLayout + Button`，文字/背景色显式指定（`0xFFFFFFFF` / `0xFF37474F`），每个按钮显示 `文件名 / 大小 / 修改时间`。任何主题下都可见可点，顺带改善了大屏触摸体验。

## 4. 桌面运行时 `dev` tmpfs 是 busy，普通 umount 卸不掉

**现象**：从菜单恢复（此时桌面正开着）必被护栏拦下；先手动停掉桌面再恢复就正常。

**原因**：`/data/data/com.termux/files/ubuntu/dev` 是独立 tmpfs，chroot 会话里还有进程持有引用，普通 `umount` 返回失败；护栏看到 `/proc/mounts` 仍有记录就拒绝 `rm -rf`（这个护栏是防止 bind 穿透删宿主文件的，必须保留）。

**修法**：`umount -l`（lazy detach）+ 多轮遍历 + 每轮复查 `/proc/mounts`。注意 `/proc/mounts` 里同一挂载会以 `/data/data`、`/data/user/0`、`/data_mirror` 三种别名出现，卸载真实路径后三条会一起消失，**不要**用 `grep -v` 把proc/sys 过滤掉来判断「干净」，那会误判。

## 5. `copyAssetIfNeeded` 按文件大小比较，会让升级后的新脚本不生效

**现象**：APK 更新了 assets 脚本，设备上仍跑旧脚本（旧脚本大小恰好和新版不同才碰巧被覆盖）。

**修法**：脚本类（`.sh` / `.pa`，几 KB）**总是覆盖**；大资源包（`.bin`，十几 MB）保留大小比较，避免每次导入重复复制。

## 6. `-PappVersionName` 根本没写进 APK

`app/build.gradle` 原本只读环境变量 `TERMUX_APP_VERSION_NAME`，构建脚本一直传 `-PappVersionName=0.118.0-vXX` 全部无效，所有版本 `versionName` 都是 `0.118.0`。v37 起同时支持 `-P` 参数，装完 `dumpsys package com.termux | grep versionName` 能看到真实版本。

## 7. 备份 `tar | gzip` 取的是 gzip 的退出码

管道 `$?` 是最后一个命令（gzip）的退出码，tar 中途 `Permission denied` 会被掩盖成「备份成功」。修法：拆成两步（先落未压缩 tar，检查 tar 退出码，再 gzip），或至少校验产物大小 + `gzip -t` + 关键文件在包内。

## 8. 备份/恢复的执行身份不能看「当前模式标记」

从 root 切到非 root 后，rootfs 里 `/usr`、`/root` 仍是 `root:root 700`。若按 `.force-noroot` 决定用 App uid 打包，会大量 EACCES 跳过文件，生成一个残缺包却报成功。应改为按 `isSuAvailable()`（设备**真实**能否拿到 root）决定执行身份。

## 9. 发布 SOP（务必按顺序）

1. 设备上停桌面、卸载所有运行时挂载；
2. `tools/clean_rootfs.sh` 删 Chrome profile / 缓存 / `.bash_history` / `recently-used.xbel`；
3. `tools/pack_rootfs_on_device.sh` 打包（内置护栏：还有挂载就中止）；
4. `gzip -t` + 包内 grep 个人信息关键字复查；
5. `adb pull` 回 `releases/`，上传 Release（**资源名用 ASCII**，GitHub 上传接口会把中文替换成点）。

用户主动「备份系统」走的是另一条路径：`backup-rootfs.sh` 原样保留个人信息，属用户自己的数据，不要拿它当发布包。
